# PROOFLINE v0.2.6-C2.2.2 — Functional payment and launch governance

This checkpoint extends C2.2.1 with functional foundations only. Visual-language/iconography work remains deferred to C2.3.

## Payment foundation

- Provider-neutral payment domain with Redsys, PayPal and bank-transfer/SEPA provider codes.
- No PAN, CVV, PayPal password or customer bank credentials are stored by Proofline.
- Safe method metadata, method lifecycle, change history and transaction ledger.
- Public start flow records the intended payment provider without collecting payment credentials.
- Commercial paid provisioning is blocked until payment setup is READY or VERIFIED.
- Evaluation workspaces can still be provisioned before paid payment setup; conversion to ACTIVE is gated.
- Workspace Billing exposes current method, history, transactions and a controlled change request for Owner/Billing Admin roles.
- Control exposes current/pending methods, activation/replacement history and manual transaction or bank-transfer reconciliation.
- Provider adapter contract and environment placeholders are ready for later real Redsys/PayPal SDK + webhook integration.

## Assessment launch governance

- Launch readiness now includes explicit organization branding and participant-preview approval.
- Branding launch eligibility requires a saved branding record, enabled state, logo and accessible colors.
- The Workspace is not globally blocked: users may prepare an assessment while branding remains pending.
- ACTIVE transition is blocked until questionnaire, Proofline Check, population, privacy, participant notice, recipients, locale, branding, preview approval, subscription and plan-capacity gates pass.
- Preview approval stores a hash of participant-visible content. Question, notice or branding changes automatically make the prior approval stale without deleting its audit history.
- Frozen assessment versions preserve branding and visual-approval provenance.
- Report snapshots preserve launched branding metadata for future visual PDF rendering.

## Local validation order

From the PROOFLINE root in the integrated VS Code PowerShell terminal:

```powershell
npx -y pnpm@10.15.1 db:generate
npx -y pnpm@10.15.1 db:push
npx -y pnpm@10.15.1 auth:bootstrap-local
npx -y pnpm@10.15.1 demo:functional-fixtures
npx -y pnpm@10.15.1 audit:static
npx -y pnpm@10.15.1 typecheck
npx -y pnpm@10.15.1 runtime:check
```

If `db:push` reports a destructive/data-loss change or asks for `--accept-data-loss`, stop and review it. Do not accept automatically.

Do not run `db:seed`, `infra:reset`, Docker volume deletion or database reset for this patch.
