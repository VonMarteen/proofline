# PROOFLINE — Security, Privacy & Trust Baseline v0.3

## 1. Security objective

Proofline processes organizational assessments that may contain sensitive perceptions, free text and potentially high-impact employment context. Security and privacy must be architectural controls, not contractual promises only.

## 2. Data classification

### Public
Marketing content and intentionally public Marketplace metadata.

### Internal
Operational data without customer-sensitive content.

### Confidential
Organization settings, contracts, billing, aggregate reports subject to authorization.

### Restricted
- direct participant identity;
- raw individual responses where identifiable/pseudonymous;
- sensitive free text;
- support exports containing PII;
- secrets/keys;
- privileged legal/security evidence.

Every storage object/job/log field should inherit a classification.

## 3. Four-surface isolation

### Public Site
No access to tenant data. Marketing analytics/cookies isolated.

### Client App
Authenticated organization-scoped access.

### Respond
Token-scoped. No authenticated tenant session. No marketing trackers. Strict CSP and minimal third-party scripts.

### Control
Separate identity pool, stronger MFA, internal permissions, step-up and privileged-access workflows.

## 4. Data minimization

Before assessment launch, Proofline displays a data manifest:

| Field | Source | Purpose | Required | Retention |
|---|---|---|---|---|

No field without purpose should be collected.

System fields that are not business data — timestamps, request ids, security metadata — must also be assessed for necessity and retention.

## 5. Identity Vault

Direct identifiers:

- logical separation;
- application-level envelope encryption;
- KMS protected master keys;
- blind indexes for necessary lookup;
- separate repository/service permissions;
- no analytics access.

## 6. Authorization

Policy inputs:

- actor;
- organization;
- assessment;
- resource classification;
- data scope;
- action;
- support access session;
- legal/entitlement gates.

No UI-only authorization.

## 7. PostgreSQL RLS

RLS provides defense in depth for tenant rows.

Rules:

- client runtime cannot disable RLS;
- migration/admin role not used by app;
- tests for cross-tenant leakage are mandatory;
- background jobs set explicit tenant scope.

## 8. Privileged access

`SupportAccessSession`:

- requesting employee;
- organization;
- purpose;
- capabilities;
- sensitivity;
- client approval flag if required;
- start/end;
- step-up authentication;
- revocation;
- immutable audit link.

Restricted access defaults to deny.

## 9. Encryption

- TLS in transit;
- RDS encryption;
- S3 SSE-KMS;
- secrets in Secrets Manager;
- selected PII encrypted at application layer;
- backup encryption;
- key rotation and access review.

## 10. Logging

Logs must not contain:

- raw participant answers;
- participant tokens;
- passwords/passkeys secrets;
- decrypted identity fields;
- full payment data;
- AI prompts containing Restricted content unless a dedicated approved secure trace store exists.

Use identifiers and trace ids.

## 11. Legal evidence security

Legal acceptance records are append-only from normal application paths.

Store:

- document version id;
- action;
- timestamp;
- actor reference;
- content hash;
- scope;
- locale;
- evidence request/session id.

Changes require superseding records, not mutation.

## 12. Participant privacy

- token has no PII;
- client cannot infer completion details beyond configured mode;
- no precise response timestamp exposed by default;
- free-text PII redaction before client display when configured;
- minimum cohorts;
- differencing/inference protection;
- safe aggregation;
- no hidden fingerprinting.

## 13. Cookie / tracker separation

Marketing cookies exist only on `site` when approved.

`respond` has no advertising trackers.

Product analytics on `web` and `control` use dedicated privacy review and tenant configuration.

Theme/language storage cannot be repurposed for behavioural profiling.

## 14. AI security

- no browser-to-provider calls;
- approved feature registry;
- least-data prompt construction;
- PII redaction/pseudonymization;
- prompt injection handling for imported/free-text content;
- structured outputs/schema validation;
- provider retention configuration;
- model/version provenance;
- no statistics generated by LLM;
- no autonomous employment decisions.

## 15. File security

Imports:

- size/type allowlists;
- malware scanning;
- parser isolation;
- macro rejection where applicable;
- no active content execution;
- quarantine state;
- object-level encryption;
- signed URL expiry.

Reports:

- access control by audience;
- expiring links;
- revocation;
- watermark option for sensitive reports;
- no public S3 objects.

## 16. Billing security

- no card data stored by Proofline;
- Stripe-hosted/approved payment flows;
- webhook signature verification;
- idempotency;
- replay protection;
- entitlements controlled internally;
- refunds/credits audit.

## 17. Secure SDLC

CI baseline:

- lint/typecheck;
- unit/integration/E2E;
- SAST CodeQL;
- dependency review;
- secret scan Gitleaks;
- container scan Trivy;
- SBOM;
- IaC scan;
- DAST staging;
- branch protection;
- signed/provenance-aware releases where practical.

## 18. OWASP / application security

Target OWASP ASVS 5.0 profile appropriate to the product.

Special focus:

- broken access control;
- tenant isolation;
- IDOR;
- SSRF from report renderer/imports;
- XSS from rich questions/comments;
- CSRF;
- session fixation;
- injection;
- unsafe deserialization;
- webhook replay;
- rate limits/abuse;
- file parsing.

## 19. Backup / DR

- encrypted automated backups;
- PITR for RDS;
- versioning where justified;
- cross-region EU copy;
- documented RPO/RTO before production;
- restore tests, not backup existence only.

## 20. Privacy operations

- data inventory;
- retention matrix;
- DSR workflows;
- deletion verification;
- legal hold;
- subprocessor register;
- incident/breach workflow;
- DPIA support pack;
- audit export.

## 21. Launch security gate

Required before production:

- threat model;
- external pentest;
- tenant isolation test suite;
- privacy/differencing test suite;
- restore drill;
- secrets review;
- privileged-access tabletop;
- cookie/consent verification;
- legal evidence verification;
- incident-response tabletop;
- DPA/subprocessor review;
- AI feature classification review.
